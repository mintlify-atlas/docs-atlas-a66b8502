This page walks through the five most common patterns in functools-kit using complete, runnable TypeScript examples taken directly from the library. Each example shows the import and a realistic usage scenario. You can pick up any pattern independently — they do not depend on each other.

<Note>
  Make sure you have [installed functools-kit](/installation) and configured TypeScript 5.0+ before running these examples.
</Note>

## Debounce and throttle

Use `debounce` when you want to delay a function call until after a quiet period, and `throttle` when you want to allow at most one call per time window. Both are common for handling UI events or rate-limiting outbound requests.

<Tabs>
  <Tab title="Debounce">
    `debounce` waits for the specified millisecond delay after the last call before executing. Useful for search inputs, resize handlers, or any event that fires in bursts.

    ```typescript
    import { debounce } from "functools-kit";

    const onResize = debounce(() => recalcLayout(), 300);

    // Attach to a resize event — recalcLayout runs only after
    // the user stops resizing for 300 ms
    window.addEventListener("resize", onResize);

    // Call .clear() to cancel a pending invocation
    // onResize.clear();
    ```
  </Tab>
  <Tab title="Throttle">
    `throttle` executes on the leading edge and then ignores subsequent calls until the time window expires. Useful for scroll handlers, mousemove tracking, or rate-limiting API calls.

    ```typescript
    import { throttle } from "functools-kit";

    const onScroll = throttle(() => updateHeader(), 100);

    // updateHeader fires immediately on the first scroll event,
    // then at most once every 100 ms
    window.addEventListener("scroll", onScroll);

    // Cancel any pending leading-edge call
    // onScroll.clear();
    ```
  </Tab>
</Tabs>

## Memoize with TTL

`ttl` wraps an async function and caches its return value per key for a configurable duration. When the TTL expires, the next call for that key re-executes the underlying function. This is the right tool for caching remote data that changes over time.

```typescript
import { ttl } from "functools-kit";

const getUser = ttl(
  async (userId: string) => fetchUser(userId),
  { key: ([id]) => id, timeout: 60_000 }
);

// First call fetches from the origin
const user = await getUser("user-123");

// Subsequent calls within 60 s return the cached value
const same = await getUser("user-123");

// After 60 000 ms, the cache expires and the next call
// re-fetches from the origin
```

<Tip>
  The `key` function receives the arguments tuple and must return a string that uniquely identifies the cache entry. Use it to support multiple distinct cache slots — one per `userId`, for example.
</Tip>

For caching that should never expire, use [`memoize`](/api/memoize) instead. For argument-change-based invalidation without a time limit, use [`cached`](/api/cached).

## Cancelable promises

`cancelable` wraps an async function so that any in-flight call can be cancelled. The cancelled call resolves to the special `CANCELED_PROMISE_SYMBOL` sentinel rather than throwing, which makes it easy to handle gracefully.

```typescript
import { cancelable, CANCELED_PROMISE_SYMBOL } from "functools-kit";

const fetchData = cancelable(async (url: string) => {
  const res = await fetch(url);
  return res.json();
});

// Start a fetch
const result = await fetchData("/api/data");

// Guard against the cancelled case before using the result
if (result === CANCELED_PROMISE_SYMBOL) return;

console.log(result);

// Cancel any currently in-flight call — e.g. on component unmount
fetchData.cancel();
```

<Warning>
  Always check for `CANCELED_PROMISE_SYMBOL` before using the result. Failing to do so means your code may try to process `CANCELED_PROMISE_SYMBOL` as real data if a cancellation occurs.
</Warning>

A common pattern is to call `fetchData.cancel()` in cleanup logic — for example, in a React `useEffect` cleanup function or when navigating away from a page — and then check the sentinel at the top of your handler.

## Observer and reactive streams

`Subject` is the core reactive primitive. It lets you push values with `.next()` and compose transformations using operators like `.filter()`, `.map()`, and `.debounce()` before connecting a subscriber.

```typescript
import { Subject } from "functools-kit";

const subject = new Subject<number>();

subject
  .filter(n => n % 2 === 0)   // only even numbers
  .map(n => n * 2)             // double them
  .debounce(200)               // wait for a 200 ms quiet period
  .connect(value => console.log(value));

subject.next(1); // filtered out (odd)
subject.next(2); // passes filter → 4, debounced
subject.next(4); // passes filter → 8, debounced; logs 8 after 200 ms
```

For more advanced source creation and stream composition, use `Source` and `Operator`:

```typescript
import { Source, Operator } from "functools-kit";

// Deduplicate, skip the first, and take three from a static array
Source.fromArray([1, 2, 3, 2, 1, 4, 5])
  .operator(Operator.distinct())  // remove duplicates: 1, 2, 3, 4, 5
  .operator(Operator.skip(1))     // skip first: 2, 3, 4, 5
  .operator(Operator.take(3))     // take three: 2, 3, 4
  .connect(value => console.log(value));

// Emit values every 100 ms and batch them into groups of three
Source.fromInterval(100)
  .operator(Operator.group(3))    // [0,1,2], [3,4,5], ...
  .connect(batch => console.log(batch));
```

<Tip>
  Use `BehaviorSubject` instead of `Subject` when late subscribers need to receive the current value immediately on subscription — common for state management patterns.
</Tip>

## Execution pool

`execpool` limits the number of async function calls that run concurrently. Calls that arrive when the pool is full are queued and executed as slots become available. This prevents overwhelming downstream services or exhausting system resources.

```typescript
import { execpool } from "functools-kit";

const processFile = execpool(
  async (path: string) => heavyProcessing(path),
  { maxExec: 4, delay: 50 }
);

const files = ["a.dat", "b.dat", "c.dat", "d.dat", "e.dat", "f.dat"];

// All six calls are submitted immediately, but at most four
// run concurrently. The remaining two wait in the queue.
await Promise.all(files.map(f => processFile(f)));
```

The `delay` option (in milliseconds) adds a gap between starting each queued execution, which is useful for APIs that enforce a rate limit on top of a concurrency limit.

For strict sequential ordering instead of a pool, use [`queued`](/api/queued). For mutual exclusion in a critical section, use [`Lock`](/api/lock).
